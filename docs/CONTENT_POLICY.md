# 콘텐츠 정책 — 선택형 동결, 실무형 확장

이 문서는 앞으로의 모든 콘텐츠 추가에 적용되는 **구속력 있는 규칙**입니다.
새 문항을 만들기 전에 여기부터 읽으세요. `tests/app.test.cjs` 가 1~2번을 기계로 강제합니다.

---

## 왜

문항 수는 부족하지 않습니다. **유형이 편중돼 있습니다.**

분할 시점(2026-07-26) 기준 7,409문항의 구성:

| 유형 | 수 | 비율 |
|---|--:|--:|
| choice | 5,690 | 76.8% |
| input | 1,216 | 16.4% |
| code·py·sql | 357 | 4.8% |
| review | 107 | 1.4% |
| log | 40 | 0.5% |

인출 모드가 선택형 전체에 걸려 있어 *체감* 비율은 이보다 낫습니다. 하지만 저장된 구성은
여전히 "고르는 훈련"에 쏠려 있고, 실제 개발자가 하는 일 — 만들고, 디버깅하고, 리뷰하고,
장애 원인을 짚는 일 — 에 해당하는 콘텐츠는 7%가 안 됩니다.

이 앱의 목표는 문제를 많이 푸는 것이 아니라 **직접 만들고·디버깅하고·리뷰하고·판단하는
훈련**입니다. 콘텐츠 구성이 그 목표를 반영해야 합니다.

---

## 목표 비율 (확정)

`choice` 는 **삭감하지 않습니다.** 기초 개념은 반복이 필요하고, 중복처럼 보여도 난이도·맥락이
다른 문항이 있습니다. 대량 삭제는 실사용 데이터를 본 뒤 "거의 안 풀리는 중복" 만 정리하는
방식으로 나중에 합니다. 그때까지 5,690 은 상한이자 하한입니다.

또한 학습 효과는 비율보다 **유형 배치**가 더 큽니다. 한 레슨 안에서
`선택형 → 인출(input) → 리뷰 → 구현` 순으로 놓이면 선택형이 60% 여도 체감은 실전형입니다.
비율은 그 배치를 가능하게 하는 재고량의 문제로 봅니다.

| 유형 | 목표 비율 | 지금 (7,612 기준) |
|---|--:|--:|
| choice | 55~60% | 74.8% (동결) |
| input | 18~20% | 16.0% |
| 실행형 (code·py·sql) | **12~15%** | 4.7% |
| review | 5~8% | 3.0% |
| log | 2~4% | 1.6% |

choice 를 5,690 에 고정하면 목표 비율에서 총량이 역산됩니다.

| choice 비율 | 총 문항 | input | 실행형 | review | log |
|--:|--:|--:|--:|--:|--:|
| 60% | 9,483 | 1,707 (+491) | **1,138 (+781)** | 474 (+245) | 190 (+70) |
| 55% | 10,345 | 1,862 (+646) | **1,241 (+884)** | 517 (+288) | 207 (+87) |

**가장 큰 구멍은 실행형입니다** — 리뷰(+245)나 로그(+70)의 3배가 넘습니다.
실행 엔진이 있는 트랙(JS `code`, Python `py`, SQL `sql`)에서만 만들 수 있으므로,
Java·C·C++·Go 는 실행형 대신 `input`(출력 예측·복잡도 계산)과 `review` 로 채웁니다 —
그쪽이 input 목표(+491)에도 그대로 기여합니다.

빌드 랩 Day 와 Git 미션은 실행 훈련이지만 문항으로 세지 않습니다. 40 Day + 25 미션을
더해도 실행형 문항 수는 422 이므로, 목표를 채우려면 실행형 문항 자체를 늘려야 합니다.

## 규칙

### 1. choice 는 늘리지 않는다 (강제됨)

전체 `choice` 문항 수는 **5,690개를 넘을 수 없습니다.** 테스트가 막습니다.

예외는 두 가지뿐입니다.
- 기존 choice 문항을 더 나은 것으로 **교체**할 때 (총량 불변)
- 완전히 새 트랙을 열 때 — 이때도 그 트랙의 choice 비율이 60%를 넘지 않아야 합니다

새 트랙이 아니라면, 선택형으로 밖에 표현 못 할 것 같은 지식은 대개 `input`(단답 인출) 이나
`review`(그 지식을 어긴 코드를 골라내기)로 바꿔 쓸 수 있습니다.

### 2. 지정된 트랙에는 review 가 있어야 한다 (강제됨)

다음 트랙은 `review` 문항을 **트랙당 30개 이상** 가져야 합니다.

`react` · `sysd`(시스템 설계) · `os` · `net` · `web`(HTML/CSS) · `ai` · `ml` ·
`pandas` · `numpy` · `mleval` · `backend` · `devops`

(`arch` 는 컴퓨터 구조 트랙입니다 — 시스템 설계는 `sysd` 입니다. 혼동 주의.)

테스트가 트랙별 개수를 확인합니다. 목표에 도달할 때까지는 테스트에 현재 달성치가
기록되며, 뒷걸음질(회귀)이 막힙니다.

### 3. review 는 문법 오류를 묻지 않는다

컴파일러가 잡아주는 건 리뷰 대상이 아닙니다. 실제 리뷰에서 잡히는 것을 씁니다.

성능(N+1·불필요한 재계산·복잡도) · 메모리 낭비 · Race Condition · 동시성 ·
Null·경계 처리 · 리소스 누수(fd·커넥션·구독·타이머) · 보안(SQL Injection·XSS·CSRF·
인가 누락·시크릿 노출) · 잘못된 API 사용 · 리팩터링 포인트

**오탐 후보(distractor)를 반드시 섞습니다.** "정상인데 결함처럼 보이는" 항목이 없으면
전부 고르기만 해도 맞습니다. 채점이 집합 일치라서, 오탐을 하나라도 고르면 틀립니다 —
이게 리뷰 훈련의 핵심입니다.

### 4. log 는 "증상"이 아니라 "원인"을 묻는다

로그에서 고를 것은 **가장 먼저 고쳐야 하는 원인 줄**입니다.
500 폭증·502·OOM·타임아웃 같은 *따라온 증상* 줄은 distractor 로 넣습니다.

다룰 로그: Linux · Docker · Kubernetes · Nginx · Apache · Spring Boot · Node.js ·
Express · PostgreSQL · MySQL · Redis · Kafka · RabbitMQ · AWS CloudWatch · CI/CD ·
GitHub Actions

### 5. 실행 엔진이 없는 트랙도 실무 훈련이 된다

Java·C·C++·Go 는 브라우저 실행이 없습니다. 그래도 다음은 전부 가능합니다.

디버깅(버그 코드 → 원인 지목) · 코드 리뷰 · 출력 예측 · 시간복잡도 개선 · 리팩터링

실행 엔진이 없다는 이유로 선택형을 더 붓지 마세요.

### 6. 프로젝트·빌드 랩은 "고르는" 것이 아니라 "만드는" 것이다

`Redis 를 쓸까요, MongoDB 를 쓸까요?` 같은 선택형 프로젝트는 만들지 않습니다.
사용자가 직접 설계하고, 코드를 쓰고, 테스트를 통과시키고, 리팩터링합니다.

빌드 랩 Day 는 `요구사항 → 설계 → 구현 → 테스트 → 리뷰 → 리팩터링 → 배포` 흐름을
따릅니다. Day 는 앞 Day 의 코드 위에 쌓입니다.

### 7. 검증 없는 콘텐츠는 넣지 않는다

- review·log: 결함/원인이 1개 이상, 전부는 아닐 것. 후보 문구 중복 금지(채점 불가)
- 실행형: 시작 코드로는 **실패**하고 참조 해답으로는 **통과**하는 것을 기계로 확인
- 빌드 랩 Day: 위와 같음 + 앞 Day 해답으로는 다음 Day 가 통과되지 않을 것
- Git 미션: 시작 상태 미통과 · 읽기 전용 명령으로 미통과 · 정해진 해결 경로로 통과
- 출력 예측: 정답을 손으로 적지 않는다. javac·gcc·g++·go 로 실제 실행해 표준출력과 대조한다
  (앱 채점의 정규화 규칙 — 소문자·공백 제거 — 과 같은 기준으로 비교해야 한다)

## 언어별 유형 매트릭스 (확정 · 강제됨)

같은 문항 수라도 **그 언어답게** 유형이 채워져야 체감이 달라집니다. 비율만 맞추고
어느 트랙이든 똑같이 선택형이면 "읽는 앱" 입니다. 트랙마다 그 언어를 실제로 쓸 때
하는 일이 있고, 그 일에 대응하는 유형이 있습니다.

| 트랙 | 그 언어답게 넣을 것 | 대응 유형 |
|---|---|---|
| Python | 코드 작성 · 디버깅 · 코드 리뷰 · 출력 예측 | `py` · `py`(cat:debug) · `review` · `input` |
| JavaScript | 코드 작성 · 디버깅 · 코드 리뷰 · DOM/비동기 디버깅 | `code` · `code`(cat:debug) · `review` · `code` |
| SQL | 쿼리 작성 · 실행 결과 예측 · 성능 개선 · 리뷰 | `sql` · `input` · `review`(cat:perf) · `review` |
| Java | 출력 예측 · 디버깅 · 코드 리뷰 · 리팩터링 | `input` · `review`(cat:debug) · `review` · `review` |
| C | 포인터 추적 · 출력 예측 · 디버깅 · 리뷰 | `input` · `input` · `review`(cat:debug) · `review` |
| C++ | STL · 메모리 · 출력 예측 · 리뷰 | `review` · `review` · `input` · `review` |
| Go | goroutine · channel · race · 리뷰 | `review` · `input` · `review` · `review` |
| React | 버그 찾기 · Hook 리뷰 · 렌더링 디버깅 | `review`(cat:debug) · `review` · `review` |
| HTML/CSS | 레이아웃 수정 · 접근성 리뷰 | `review` · `review` |
| 운영체제 | 로그 · 디버깅 · 코드 리뷰 | `log` · `review`(cat:debug) · `review` |
| 네트워크 | 로그 분석 · 장애 원인 찾기 | `log` · `log` |
| Git/DevOps | Git 시뮬레이터 · 로그 | 미션 · `log` |

정적 언어(Java·C·C++·Go)의 "디버깅" 은 실행 엔진 없이도 성립합니다. 버그가 있는

동작은 그대로입니다. 출력 예측·포인터 추적은 `input` 이며, 정답은 손으로 적지 않고

`code` 든, 버그를 앞에 놓고 원인을 찾게 만들면 디버깅입니다.

### 실행형 난이도 층 (확정)

실행형 문항에는 `lv` 를 붙여 층을 나눕니다. 같은 트랙 안에서도 층이 섞여 있어야
"만들 줄은 아는데 못 고치는" 또는 그 반대의 공백이 드러납니다.

| 층 | 하는 일 | 판정 |
|---|---|---|
| L1 | 요구된 것을 처음부터 만든다 | 빈 시작 코드 → 검사 전부 통과 |
| L2 | 깨진 코드의 원인을 찾아 고친다 | 시작 코드가 실패 → 원인 한 곳 수정으로 통과 |
| L3 | 최소 수정으로 통과시킨다 | 구조는 그대로 두고 한두 줄 |
| L4 | 요건을 더 붙여 개선한다 | 접근성·반응형·복잡도까지 만족 |

### 브라우저에서 실행 가능한 언어 (사실 정리)

| 언어 | 실행 | 방식 |
|---|---|---|
| JavaScript | ✅ | iframe 안에서 직접 실행 |
| Python | ✅ | Pyodide (WASM) |
| SQL | ✅ | sql.js = SQLite WASM (852KB, 지연 로드) |
| **HTML/CSS** | ✅ | **브라우저 자체가 엔진** — 렌더 후 DOM·계산된 스타일 검사 |
| Java · C · C++ · Go | ❌ | 컴파일러를 브라우저에 넣을 수 없다(수백 MB). 대신 **실제 컴파일러로
  정답을 검증한** 출력 예측 272 + 디버깅 리뷰 80 으로 훈련한다 |

오프라인 단일 파일 원칙을 지키는 한 정적 컴파일 언어의 브라우저 실행은 불가능합니다.
"실행되는 척" 하는 시뮬레이터는 만들지 않습니다 — 틀린 결과를 가르치게 됩니다.
